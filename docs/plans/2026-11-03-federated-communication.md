## 1. 目标与范围

让不同 DSH 实例中的人和 Bot 进入同一个群，或进行双方私聊。各实例可以在不同机器、不同 IP 上，也可以在同一台机器上运行。消息应投递到正确的身份和会话，正常断线、重试和进程重启后能够恢复，不静默丢失或因重传重复展示、重复入箱。

用户最终确认的范围是**通信**。需求、设计、审核、开发和进度都只是消息中的业务内容；这些内容如何驱动工作，由 AI 或外部系统负责。

### 首版包含

1. 人类与 Bot 的稳定身份、所属实例及授权联系人。
2. 多人人类与 Bot 混合成员的共享群；各端直接看到同一份允许读取的历史。
3. 人到人、人到 Bot、Bot 到人、Bot 到 Bot 的双方私聊。
4. 建群、邀请、加入、退出、移除成员，以及群内提及、引用回复。
5. 远程成员标识、明确的发送者、接收对象与会话。
6. 文本和 Markdown 消息；引用关系只引用本会话内的消息。
7. 持久化收发队列、回执、幂等、会话顺序、断线补发与重启恢复。
8. 向真正位于归属实例的 Bot 收件箱投递消息；人类收件只更新界面与未读。
9. 单机两个 DSH Web 实例的开发环境和自动化验收；真实不同 IP 作为后续网络部署验证。

### 明确不包含

- 任务管理、项目管理、任务状态机、设计审批、开发审批、自动开发流程。
- `TaskCoordinator`、`TaskExecutor`、跨会话业务任务绑定或按任务切换执行权限。
- 远程终端、远程文件系统挂载、远程修改另一个实例的模型、工具权限或密钥。
- 同步 `DSH_HOME`、原有私聊历史、内部 Session、Bot 私有记忆或团队记忆。
- 联邦群记忆自动同步；首版不为联邦群启动各端独立的群记忆复盘。
- 任意附件传输、音视频、端到端加密、自动高可用和多协调服务之间的互联。

历史讨论中扩大到任务管理、版本化业务审批等内容，已经被用户明确排除。实施者不能根据那些旧建议扩大范围。首版不支持的附件必须在发送前明确提示，不能当成本地路径静默发送或丢弃。

## 3. 用户场景与消息边界

实例 A 上有人 A 和 Chief J；实例 B 上有人 B 和 Chief K。共享群 G 的成员为 A、J、B、K。

| 行为 | 正确的通信结果 |
|---|---|
| A 私聊 J | 进入 A—J 的私聊，只对该会话参与者可见 |
| J 在 G 中 `@K` | A、J、B、K 的授权视图同步显示消息；只有按群规则选定的 Bot 接收推理输入 |
| K 给 B 发私聊 | 进入 K—B 的私聊，通知 B；不能因此再次唤醒 K |
| B 回复 K | 进入同一个 K—B 私聊，并投递到 K 对应该会话的本地收件箱 |
| A 或 J 在 G 中 `@K` 询问进度 | 作为 G 内普通消息交给 K；通信层不查询或维护开发任务进度 |
| B 打开 G | 直接读取与 A 同源的群消息，不需要 K 转述，也不要求 K 的模型正在运行 |
| B 私聊 K 调整方向 | 保留在 K—B 私聊；不会自动复制进 G 或自动控制 K 在 G 中的执行 |

同一个 Bot 出现在多个会话中，不代表这些会话共享输入。需要跨会话传达时，由发送方明确选择目标会话，重新发布允许共享的内容。通信层可以附带引用关系，但不能借引用绕过会话权限。

## 4. 架构决策

### 4.1 单一共享通信服务

首版部署一个轻量通信服务，建议作为仓库内独立 Node.js 包，例如 `communication-server/`。服务使用一个 SQLite 数据库保存身份、联系人、成员关系、消息、投递记录和同步位置。

每个 DSH 的 DS-Bot 插件主动建立 WebSocket 连接。单机测试连接 loopback；跨机器部署使用可达地址与 WSS。协调服务可以运行在一台常开电脑上，不要求购买云服务。

服务的职责是认证、持久化、路由、补发与按群规则选定消息接收者。它不运行模型，也不理解消息中的需求、审核或开发流程。

单一服务有一个明确的群事件顺序，减少第一版的复杂度。服务不可用时，各端保存未提交的待发消息；恢复后按协议继续。已有纯本地 Bot 和群保留现有使用路径。

### 4.2 每个实例一个通信适配层

建议新增 `ds-bot/src/host/federation/`，包含：

- 身份注册、联系人目录和连接生命周期；
- 本地持久化 outbox/inbox、重试和回执；
- 会话映射、群消息投影和历史分页；
- DSH 收件箱适配、Bot 发言导出与双向持久化对账；
- 人类消息入口和 Bot 通信工具入口。

远程联系人不伪造本机 `sessionId`。只有归属本机的 Bot 能调用本机 DSH 运行接口；远端成员的消息发送到其归属实例处理。

### 4.3 显示、通知、Bot 入箱分开

| 路径 | 行为 | 是否启动模型 |
|---|---|---|
| 群/私聊事件同步 | 保存事件、更新消息列表与未读 | 否 |
| 人类收件 | 更新对应私聊或群的通知 | 否 |
| Bot 收件 | 验证目标和会话，向绑定的本地 Session 入箱 | 按 DSH 的正常消息机制 |
| Bot 发言回传 | 把明确发布的文本送到原会话或指定会话 | 仅由唯一群规则决定后继接收者 |

收到共享事件时不能再次把它当成一条本地新发言广播。历史回放只恢复显示，不能重新解析 `@` 产生投递；离线期间已经创建、尚未消费的 `deliveryId` 则继续原来的收件流程。两条恢复路径必须分开。

Bot 已生成并持久保存的可发布回复，也必须能恢复进入 outbox。保存稳定的源输出到 `messageId` 映射及导出游标，避免宿主在“已生成回复、尚未发出”之间重启后永久漏掉回复。

### 4.4 通信视图独立持久化

联邦群和新增通信私聊由 DS-Bot 的通信库保存完整历史，并在插件主区域显示。复用现有侧栏、头像、气泡、主题和详情组件。

不以向 DSH 内部日志写入任意自定义事件为实现前提；也不伪造 assistant/tool 记录。真正投给 Bot 的输入使用公开 DSH 消息 API。公开 API 的持久化和恢复能力在 P0 先验证。

已有本地私聊历史不自动上传或拼接。新通信会话的入口必须清楚标明参与者和来源；不能把两个不同会话显示成无法区分的同名入口。若希望复用已有的人机私聊入口，应先证明映射、收件和回放正确，不能直接把新会话的内容塞到任意当前 Session。

## 5. 身份、成员和可见性

### 5.1 身份

- `instanceId` 标识一个独立运行数据实例，与 IP、机器名、进程 PID 分离。
- 人类有稳定身份，Bot 有稳定身份和所属实例；显示名可变，路由 ID 不变。
- 首版每个 DSH 仍保留一个本地所有者；将这些所有者注册为共享通信中的不同人类成员。
- 每个实例只可代表被注册给自己的身份发言。Bot 工具不能选择一个人类 ID 伪装发送者。
- 复制数据来新建独立测试实例时必须重新生成身份；不能让 A、B 用同一个已注册实例 ID 同时上线。

### 5.2 群与私聊

- 群成员可以同时包含人和 Bot；群管理员与本机 Main Bot 身份分别校验。
- 私聊固定两个参与身份；Hub 对规范化双方身份键设置唯一约束，双端同时首次创建也返回同一个会话，关闭窗口不解除此绑定。
- 新群/私聊可从 UI 或有相应授权的 Bot 工具建立；仅对已配对、允许发现的联系人操作。
- 配对及允许公开哪些 Bot 由实例所有者设置，正常范围内的每条消息无需反复确认。
- 新成员默认从加入的事件位置开始读取；需要共享更早内容时，成员明确发布摘要或选定文本为新消息。
- 移除成员后停止发送后续消息；尚未交付的旧消息按协议给出撤权结果，不能静默丢弃。
- 本地隐藏、置顶、已读属于本地偏好；退群、移除成员、解散属于共享操作，界面文案必须区分。

### 5.3 远程标识

远程是相对查看实例的属性。同一 Bot 在所属实例显示为本地，在其他实例显示为远程。

标识至少出现在：联系人列表、建群选择器、`@` 菜单、消息作者、成员详情。展示名字、来源实例和在线状态；人类和 Bot 使用明确的类型标识，不能只靠颜色。

两个 Chief 同名时，菜单携带稳定目标 ID；模型名册提供唯一别名。手写含歧义的 `@Chief` 不默认选第一个。消息发布时固定提及对象，历史回放不按后来改过的名字重新路由。

## 6. 群消息的接收规则

1. 授权的人类界面能够看到群消息，不需要由模型逐条转述。
2. `@人` 只通知这个人，不自动把消息交给其 Chief。
3. `@Bot` 按稳定身份向该 Bot 的群收件箱投递。
4. `@` 多个 Bot 可以分别投递；传输排序不要求所有模型串行执行。
5. 首版提供 `admin` 和 `mentionsOnly` 两种路由模式。设置了群管理员 Bot 的群默认用 `admin`：没有活动提及的人类消息只交给该 Bot；没有管理员时默认 `mentionsOnly`，只显示而不启动模型。路由模式和版本由 Hub 保存，不允许各实例各叫一个本机 Chief。
6. Bot 的普通回复没有新提及时，不自动唤醒全群；回复关联不等于再次发起整群轮次。
7. 有效 `@` 接力不加固定跳数上限。网络重复与回音靠消息身份和投递去重解决；对话行为仍可沿用已经验证的空转检测。
8. 保留现有本地群的默认行为；首版联邦群不提供全员轮流模式，不能让界面选择一个未实现的模式。只有 `@人` 的消息也不触发默认管理员。

管理员离线时消息继续保存，待发送状态可见；不擅自改叫别的本机 Chief。人类聊天可以继续进行。

## 7. 源码改造落点

以下路径和函数基于上述固定提交核对；新增名称是实现建议。

| 位置 | 已有事实 | 实施要求 |
|---|---|---|
| `src/host/store.js` | `chatOf`、`selfOf`、`indexSessions` 假设 Bot 是本机实体，迁移会过滤未知群成员 | 远程联系人单独存储；统一身份解析与本机 Session 解析分开 |
| `src/host/roster.js` | `createRoom` 过滤本地 Bot，群 ID 起于本机 Session | 为联邦会话建立独立身份和本地映射 |
| `src/host/groups.js` | `groupSessionFor`、`roomTurn` 依赖本机成员；`postToRoom` 同时写消息和调度 | 抽离通信上下文、纯展示路径和唯一接收规则，不能重复运行旧群轮次 |
| `src/host/delivery.js` | 通过公开 `createUserMessage`、`steer/followup`、`sessions.flush` 入箱 | 封装接收端投递，并处理与通信库之间的非原子崩溃窗口；另验证 Bot 输出的持久导出 |
| `src/host/tools.js` | `message_bot` 的 `reply_to: user` 没有多人收件语义 | 新工具明确联系人/会话；不能把所有人都表示为一个裸 `user` |
| `src/host/channel.js` | 面向本机所有者的团队 API，快照包括大量本机设置 | 新增按会话授权的通信 API，不把原接口暴露给远端联系人 |
| `src/shared/mentions.js` | 文本名字匹配 | 结构化提及与唯一别名，前后端一致 |
| `src/client/index.js`、`overlays.js` | 已有侧栏替换及主区域 pane 接入 | 新通信群/私聊使用自有视图，验证焦点、滚动、切换和刷新 |
| `src/client/open-listed.js` | 只能打开本机 Session list 内的 Session | 不把远端 Bot ID 或 Session ID交给本机导航 |

代码路径以 `ds-bot/` 为根。详细分阶段落点见[实施计划](federated-communication/implementation-plan.md)。

## 8. 开发与交付原则

- 只修改 DS-Bot 和新增通信服务；遵守仓库“基于公开 API，不补丁修改 DSH”的规则。
- 先使用两个独立测试 `DSH_HOME` 和 Mock 模型完成通信验收，再做真实模型补充验证。
- 需要 API key、模型地址、账号、网络权限或用户决策时直接询问用户。可以继续不依赖该条件的工作；不能伪造配置、反复无效重试或把受阻项写成通过。
- 所有测试使用专用数据目录；不读取、重置或改写用户正在使用的 DSH 数据。
- UI 改动修改 `src/client/` 后构建 `client.js`；不手改生成文件。
- 只提交代码、配置模板、设计和脱敏证据。运行凭据、登录 token、真实会话和测试数据目录不入库。
- 本次只是方案交付，不运行新功能验收，不将任何 P0/P1 项记为已完成。

## 9. 完成定义与已知限制

首版完成以[验收文档](federated-communication/acceptance.md)的必测项目通过为准，尤其是实际两个 DSH 的正确入箱、群/私聊隔离、回执丢失重试、重启恢复，以及 DSH 入箱和 Bot 回复导出的崩溃窗口。只用一个进程里的 Mock socket 通过测试不算完成。

消息的“已送达”只证明送入正确的接收端收件箱，不证明人已读、模型已消费或任何业务动作完成。首版的验收目标是在正常网络故障和进程重启中恢复持久消息；对无法确认的 DSH 入箱或输出导出结果保留未知状态，相应用例为受阻，不能据此宣称已经达到完整收发可靠性。

单机两个端口能够验证协议和实例隔离；真实不同 IP、Host/Origin、TLS、防火墙和网络路径仍需单独验证。单服务故障时消息等待恢复，不实现自动多主切换。
