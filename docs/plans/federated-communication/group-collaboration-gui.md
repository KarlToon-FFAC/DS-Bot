## 1. 对话链与回复链的关系

**使用上共用一个入口，数据上分开。** 当前回复链说明“这条消息回复了谁”，新设计
中的对话链说明“这些消息围绕哪件事交流”。简单问答中两者常常重合；复杂群聊不能
强制等同。产品统一称“话题”，把现有“查看回复”窗口升级为“话题详情”，不另外
并列一套“对话链”按钮。迁移期可使用“查看话题与回复”。

一个话题可以包含多个回复分支、直接追加而未引用的消息、多个任务，以及多个结果
共同支撑的汇总。一条回复也可以引用别的话题作为资料；这不使两个话题合并。
每条消息有一个主要话题归属；跨话题引用作为来源链接，不复制消息或任务。

| 用户需要看清什么 | 展示单位 | 与其他单位的关系 |
| --- | --- | --- |
| 大家在哪个协作空间 | 群聊 | 包含多条话题、成员与群级权限 |
| 大家正在讨论哪件事 | 话题 | 包含消息、回复关联及关联任务 |
| 谁要完成什么，卡在哪里 | 任务 | 有输入、执行 Bot、控制人、依赖与结果 |
| 这个 Bot 此刻为什么运行/停下 | 执行回合 | 属于一个任务，记录启动、恢复、结束及公开输出关联 |

一次 @ 多个 Bot 可以建立多个独立处理项；只有明确指定协调工作才出现汇总任务。
一次普通问答也可以有轻量处理项，但不必在主消息流摆一张正式工作卡。“谢谢”
等交流没有必要产生一排任务卡。预算授权属于后台控制及必要时的状态说明，不是
第五块常驻主界面。

## 2. 常驻界面保持三栏，四个概念逐层展开

```text
┌────────────┬─────────────────────────────────┬──────────────────┐
│ 会话列表   │ 联邦协作群                      │ 群信息           │
│ 群名/未读  │ 消息  |  话题 3  |  任务 4       │ 成员/联系人/规则 │
│            ├─────────────────────────────────┤                  │
│            │ 甲：[接口故障] @A 排查接口      │ A 公告进行中     │
│            │    A 等待日志 · B 检查中        │   另 1 项等待    │
│            │ 乙：[上线公告] @A 整理公告      │ B 日志检查中     │
│            │ C ：[接口故障] 回归结果…        │ C 本群暂无工作   │
│            │                                │                  │
│            ├─────────────────────────────────┤                  │
│            │ 发送到：群聊 / 选定话题         │                  │
│            │ 固定底部输入框                  │                  │
└────────────┴─────────────────────────────────┴──────────────────┘
```

- 左侧继续是会话列表，右侧继续是群信息、按联系人归类的成员及常用设置。
- 中央默认保持时间顺序消息流。增加同一行的“消息 / 话题 / 任务”视图切换，计数
  只统计当前读者有权查看的记录。没有任务时不显示醒目的空任务区。
- 消息只增加一个短话题标签；涉及多个处理目标时，在原请求下加一行紧凑状态，
  如 `A 等待 B/C · B 已返回 · C 处理中`，避免一条“已回复”掩盖其余分支。
- 标签之外保留短引用摘要；汇总显示 `综合了 2 份结果`，点击定位来源。
- 状态变化更新原位置，不不断追加“已收到/处理中”等聊天气泡。
- 成员行可显示获准公开的本群工作摘要；同 Bot 多任务显示 `进行中 1 · 等待 1`，
  不能拿它的最近回合代表所有任务，更不能显示其其他群或私聊工作。
  本群暂无任务不能推断 Bot 全局空闲；状态过期时保留最后更新提示。
  工作摘要独立可点；原来最右侧的 `>` 继续打开成员的背景、详情与特长资料。

话题列表每行展示标题、参与者、未读、最近更新、未结束任务和需用户处理的事项。
“等待子任务”不自动算“需要用户处理”。支持只看未读、我参与、进行中；任务列表
另支持按话题、执行 Bot、请求人、状态筛选。搜索结果显示归属话题，可跳回原消息。

计数和状态来自有权限的服务端投影，而非当前聊天页里恰好加载的消息，避免渐进
加载导致任务数变化或把未加载的父消息误当新话题。读话题只影响实际看过的消息，
不能把整个群的未读一次清空。

## 3. 把现有回复窗口升级成单个大“话题详情”

顶部固定原问题/话题标题、参与者和一行工作摘要。下面切换三个视图：

| 视图 | 默认展示 | 按需展开 |
| --- | --- | --- |
| 消息 | 按时间展示该话题的公开消息，每条保留“回复谁”的摘要 | 原文、引用来源、同级分支 |
| 协作图 | 消息的分叉与多来源汇合，清楚标注引用/派发/返回 | 某一分支、已完成阶段、关联任务 |
| 任务 | 紧凑任务行：工作名称、Bot、状态、等待对象、结果入口 | 子任务、控制操作、执行记录 |

图不是默认聊天阅读方式。长图按阶段、已完成子树折叠；点击某条消息定位它的上下游，
同一公开消息只画一个节点。引用、派发、等待恢复的开关不能改变实际调度。

点击任务进入**同一个大弹窗内的任务详情页**，保留“返回话题”与浏览位置；执行
记录再作为任务详情内的折叠区。复杂操作不塞在主页面末尾，也不无限叠弹窗。
窄屏改为全屏详情，输入始终贴底；关闭后恢复主群焦点、滚动位置和草稿。

底部明确本条消息的去向，例如 `话题：接口故障 · 回复：C 的回归结果`。
引用某条结果不等于给它的作者重新派活。补充既有工作时，另外显示绑定的任务；
有多个候选才提供名称/Bot/状态选择，用户不需要知道 taskId。

## 4. 任务详情与执行记录应当显示的事实

任务详情显示目标、原始请求、请求人/控制权、执行 Bot、所属话题、当前要求版本、
子任务依赖、输出去向和已提交结果。进度可显示 `依赖 1/2 已结算`，不能把子任务
数量伪装成模型工作完成百分比；其中失败或未承接必须单独标识。

执行回合显示：第几次执行、启动/恢复原因、开始与结束时间、最后获知状态、
本次生成的正式公开输出或等待状态。例：

```text
任务：A 汇总接口故障
状态：等待 B 的日志检查；C 已返回

执行 #1  已结束   触发：用户派单
          本次结果：派出 B/C 子任务，进入等待
等待中    未启动新的模型回合
执行 #2  只有收到足够结果并真正恢复后才创建
```

回合结束不等于任务完成。任务等待时没有模型在运行；断线重试消息也不是新模型
回合。“收尾补全”记录为原任务的有界补全步骤，单独标识，不伪装成新的用户请求。
重启后不知道执行状态时显示“状态待确认”及最后更新时间，不让 spinner 永久假装
正在运行，也不因心跳丢失直接判失败。

必须分开的几组状态：

| 维度 | 可展示状态 |
| --- | --- |
| 消息交付 | 本机待发送 / Hub 已接收 / 对端已收取 / 失败 / 待确认 |
| 工作 | 排队 / 执行中 / 等待子任务 / 等待用户 / 完成 / 未承接 / 取消 / 失败 / 过期 |
| 回复决定 | 已提交回复 / 明确不回复 / 尚未提交决定 / 决策失败 |

投递成功不是完成；显式不回复不是工作成功；没有消息也不证明 Bot 主动选择沉默。
对普通闲聊，“已处理，无公开回复”可以是正常结束。对要求交付的工作，必须有
明确完成依据，否则应呈现未承接、未完成或失败。公开回复和工作结果还需正确关联。

补充、停止、重派等动作绑定具体任务和版本，由宿主验证权限。取消确认明确写任务
名称、影响的子任务及已完成部分；跨机未确认前显示“正在请求停止”。转派是新任务
关联原任务，不能简单换负责人字段继承原有文件权限。

## 5. 如何归属话题而不改变执行含义

1. 在话题窗口发送、回复已有话题消息：默认继承当前主话题，可显式“另开话题”。
2. 在主群明确发起新工作：未绑定现有话题时建议新建话题；已有话题内的新任务
   保留话题归属。标题可建议生成，名称不决定授权。
3. 普通无绑定闲聊可以留在“群内交流/未归属”，不强制每条闲聊开话题或工作卡。
4. 在话题 A 引用话题 B 的结果：保留 A 的归属并显示 B 来源，不自动合并。
5. AI 可建议归属，不能仅凭语义相似改变运行任务。用户整理归属只修订展示关联，
   保留原消息、回复、任务/投递历史与审计；不补发、不恢复、不刷新预算。
6. 正在执行的任务不能因消息被移动而换输入、输出或控制权。以新目标再做一遍，
   必须明确创建新任务；话题重命名/折叠也不改变任务状态。

旧历史可依据回复关系显示现有回复链；若做语义聚合须标为建议或推测。不能从旧
正文回填“任务已完成”“等待谁”“主动不回复”等权威记录。没有数据就显示
“旧版本未记录工作状态”，而不是按看起来像成果的文字补造成功。

## 6. 当前实现与需要新增的数据

代码核对基线：`e72b0f6`。

- `ds-bot/src/host/federation/queue-store.js::thread()` 沿 `replyToMessageId` 查询
  有权限的祖先与后代；它不是任务依赖图或 Bot 调度根。
- `ds-bot/src/client/communication-thread.js` 已有树结构、分页、分支折叠能力；
  当前 `communication.js` 入口传入 `chronological:true`，按时间展示，父消息摘要
  又受 `!chronological` 限制，因此原问题/逐条引用最值得先补清楚。
- `communication-model.js::deliveryPhase()` 与 `communication-activity.js` 能展示
  投递、输入更新及部分错误；现有开始/no_reply 事件不构成完整任务或执行账本。
  当前 exporter 的 no_reply 还混有遗漏提交与发送失败，不能直接改名为“主动不回复”；
  必须等完成契约修复后才展示这种确定的决定，详见输出授权方案中的复现。
- 现有活动详情继续服务投递诊断，不改名冒充任务中心。

实施顺序：

1. 用现有可靠数据改善原问题定位、逐条引用、来源跳转与底部输入目标。无需等待
   新任务协议；仅凭这些改动不能宣称已支持完整话题/任务。
2. 增加稳定话题归属及权限投影，接入话题列表与消息标签；保留旧回复链兼容读取。
3. 接入正式 task/outcome/waiter 账本后启用任务状态、等待关系与控制操作。
4. 接入 run/continuation 审计后启用执行记录和完整协作图。旧 Hub 缺能力时只显示
   消息/回复功能及明确说明，不因 GUI 新增展示而禁止兼容的通信。

公开视图只能包含获准共享的任务状态。思考、私密草稿、内部派活、工具原始输出及
本地工作目录不得进入群话题 API；本机所有者的诊断详情用独立授权，不靠 CSS 隐藏。
依赖计数、等待对象、子任务名称和触发原因也按字段验证可见性；不能隐藏内部任务
卡，却通过 `等待某内部 Bot` 或依赖数量泄露它。无权公开的内部原因只提供获准的
概括状态。
实时更新应有版本与游标、断线补取及过期提示；更新状态不能跳动主群滚动位置或
覆盖正在输入的内容。展示和打开图本身不产生模型运行或外发。
