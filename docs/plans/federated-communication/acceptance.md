# 跨实例通信验收计划

## 1. 目标、基线与范围

验证多个 DSH 实例中的人和 Bot 可以在群聊、私聊里正确收发消息：身份准确、会话隔离、重连可恢复、消息可追踪。

- 已阅读的代码基线：`5c514ad70d5f3fd1c3b72b2e76e530bef50989d7`，DS-Bot v0.2.6。
- 本文件是实施前计划。新增通信功能、脚本、Windows 流程和跨机器流程均尚未运行，结果初始为 `NOT_RUN`。
- V1 只支持文本、Markdown 和同会话消息引用。文件、图片、音频、视频的上传/传输请求应明确返回协议规定的错误；指向外部资源的 URL 只作为普通链接传输，不保证可访问。
- 验收对象是通信与必要的 Bot 消息接收。任务分配、业务任务状态、远程工作流、设计审批和工具执行审批不属于本计划。
- Bot 是否被正确唤醒可以测试；不引入“任务完成率”“业务执行成功”等额外验收条件。
- 单次发送 Promise 成功、页面出现乐观气泡或 mock socket 收到数据，均不能独立证明消息送达。

## 2. 固定测试拓扑与术语

| 对象 | 所在位置 | 含义 |
|---|---|---|
| 实例 `a` | 本机 TCP 端口 `3101` | 独立 DSH 进程、配置、会话与插件数据 |
| 实例 `b` | 本机 TCP 端口 `3102` | 与 `a` 完全独立的第二个 DSH |
| Hub | TCP 端口 `3190` | 独立运行的通信服务及持久化数据库 |
| `A`、`J` | 实例 `a` | `A` 是人类用户，`J` 是本地 Bot |
| `B`、`K` | 实例 `b` | `B` 是人类用户，`K` 是本地 Bot |
| `G` | 两端可见的共享群 | 成员固定为 `A/J/B/K`，各端使用同一个全局群 ID |

`conversationId` 指群或私聊的全局会话 ID；`messageId` 指一条已提交消息；`deliveryId` 指向指定接收者的逻辑投递。
实际字段名可按协议映射，但测试报告必须给出映射，不能用显示名称、IP、端口或 DSH Session ID 替代全局身份。
同名显示测试另将 `J`、`K` 同时改名为 `Chief`，稳定身份及既有会话不得改变。
以下“执行一次”只指同一逻辑投递最多形成一次预期 Bot 输入，不保证 Bot 工具的外部业务副作用恰好一次。

## 3. 需求与验收用例矩阵

所有 V1 必测用例需要同时保存协议记录、持久化结果和界面或 DSH 接收证据。

| ID | 需求 | 操作与通过条件 |
|---|---|---|
| DM-01 | 人 → 人 | `A` 与 `B` 双向私聊；各自只进入同一个 A-B 会话，群与 Bot 不被唤醒 |
| DM-02 | 人 → Bot | `A` 私聊 `K`；由 `b` 上 K 对应私聊 Session 接收，回复回到 A-K |
| DM-03 | Bot → 人 | `J` 向 `B` 发私信；B 得到通知并能在 B-J 回复，不自动调用 K |
| DM-04 | Bot → Bot | `J` 向 `K` 私聊并收回回复；身份、发送方向、回复所属会话均正确 |
| DM-05 | 双向发起 | 对 DM-01 至 DM-04 交换实例方向重测，不能只实现 a 主动调用 b |
| DM-06 | 私聊隔离 | 同时使用 A-K、B-K、J-K；每条回复只返回原 conversationId |
| DM-07 | 群与私聊隔离 | K 正在处理 G 的消息时收到 A-K 私信；私信绑定对应 Session，不自动 steer 群 |
| DM-08 | 私聊身份不可冒用 | A 构造 J/B/K 的 sender 字段，宿主或 Hub 拒绝，接收者看不到冒名消息 |
| DM-09 | 双端并发建私聊 | A/B 同时首次打开对方并重试创建；返回同一 conversationId，关闭重开也不生成第二个 A-B 私聊 |
| GR-01 | 共享群 | A 建立 G 并加入 A/J/B/K；B 端出现相同群 ID、成员与已授权消息 |
| GR-02 | 任意成员发言 | A/J/B/K 分别发文本，a/b 两端按相同群序列展示一次 |
| GR-03 | 精确 @Bot | A 或 J 在 G 里 @K，只唤醒 K；B 或 K @J 对称成立 |
| GR-04 | @人 | @A、@B 产生对应人类通知，不转成 @其本地 Chief 或执行 Bot |
| GR-05 | 普通 Bot 回复 | Bot 发一条新普通回复，没有显式目标时，不自动使全体 Bot 再调用模型 |
| GR-06 | 同名成员 | J/K 都名为 Chief；菜单选择与 Bot 工具发送仍按稳定身份准确路由 |
| GR-07 | 回帖定位 | `replyTo` 指向 G 内确切消息；两端打开同一父消息，重复或同文消息不混淆 |
| GR-08 | 跨会话引用隔离 | G 的 replyTo 指向 A-K 消息时拒绝，不读取、引用或广播该私聊内容 |
| GR-09 | 远程标识 | a 显示 J 本地/K 远程；b 显示 K 本地/J 远程；发言与 @菜单均显示来源 |
| GR-10 | 多人身份 | A、B 的发言与通知归属可区分，不合并成一个无来源的 User |
| GR-11 | 默认接收模式 | admin 只调用配置的管理员；mentionsOnly 不默认调用 Bot；只有 @Human 不补叫管理员；移除管理员后模式合法 |
| GR-12 | 群成员操作 | 授权建群、邀请、接受、退出、移除可用；重试不创建重复群或成员；未接受成员不能提前收件 |
| ST-01 | 可恢复发送 | 断线时本地消息进入持久队列，重启与重连后补送，状态不虚报送达 |
| ST-02 | 幂等与顺序 | 重复、乱序、缺口和 ACK 丢失后，历史不重、不串，序列可恢复 |
| ST-03 | 崩溃恢复 | 覆盖客户端、Hub、接收端和 DSH inbox 的实际持久化崩溃窗口 |
| ST-04 | 回放与收件分离 | K 离线时收到 @K，重连恢复一次原投递；再次刷新或历史回放不增加模型调用 |
| ST-05 | Bot 回复导出 | 持久回复在 outbox 提交前崩溃后仍可补送；恢复重扫和会话换段均不重复导出 |
| AC-01 | 来源认证 | 未认证或冒用实例连接不能发布目录、订阅会话、投递或确认他人消息 |
| AC-02 | 授权变更 | 撤权后的积压消息不再交给被撤权成员；发送端得到明确终态与原因 |
| AC-03 | 入群历史 | 新成员只读 joinSeq 起的授权历史；旧摘要通过授权发送者显式分享的新消息提供 |
| AC-04 | 同机授权隔离 | B 的缓存、已读和传输游标不扩大后来加入的 K 的权限；旧引用预览、搜索和 Bot 上下文均受限 |
| UI-01 | 内置体验 | 从现有侧栏进入共享群与私聊；刷新、切换、未读、来源标识与回复均可用 |
| CT-01 | 文本边界 | 不支持的附件在客户端和宿主都被拒绝，接收端不出现伪成功气泡 |
| RG-01 | 本地兼容 | 原有本地 Bot、群聊、会话分段与发送路径保持正确，关闭联邦连接仍可本地聊天 |

## 4. 环境准备与记录

1. 从被测提交创建独立测试目录；记录操作系统、Node、DSH、DS-Bot、Hub 和数据库版本。
2. 启动两个真实 DSH 宿主并加载待测 DS-Bot。不能用两个 fake runtime 或两个 mock socket 替代。
3. 每个宿主使用独立测试数据目录；只给子进程设置所需环境，不能指向用户实际的 DSH 数据目录。
4. 通过仓库 `dev/mock-llm.mjs` 或兼容的确定性测试模型分别配置 J/K；记录所用脚本和模型行为版本。
5. 测试模型应按测试 nonce、目标 conversationId 回答，并能受控延迟；不依赖真实模型猜测路由。
6. 启动 Hub `3190`，再启动实例 a `3101`、b `3102`；保存实际启动命令和进程退出码。
7. 如实施时新增启动器，在报告中写真实文件路径与参数；本计划不声称这些脚本已经存在。
8. 为 A/B 建立各自认证身份，分别登记 J/K；使用仅本次验收有效的凭证，日志只记录凭证指纹。
9. 浏览器分别认证 a/b 并检查实例身份。可用独立 profile 方便区分；该版本的端口绑定 Cookie 允许同一浏览器双标签页，不能仅凭标签页数量认定已隔离。
10. 截图显示实例简称和测试用用户名；不得包含 token、个人目录、真实聊天或模型密钥。
11. 每条测试消息使用唯一 nonce，例如 `DM02-a-to-k-0001`，避免仅凭自然语言相同判断是否收到。
12. 开启结构化通信日志与 mock 模型调用记录，能关联 messageId、deliveryId、conversationId、接收 Session。

## 5. 正常通信实测步骤

### 5.1 四种私聊

1. A 从联系人列表打开 B，发送 `DM01-a-to-b-0001`；B 收到后回复，A 在原会话看到回复。
2. 检查 Hub 会话成员恰为 A/B；J/K 的模型调用记录没有新增由此消息造成的输入。
3. A 打开 K，发送 `DM02-a-to-k-0001`；记录 `(conversationId, K) → localSessionId` 的实际绑定。
4. 让 mock 模型回显测试 nonce；确认 K 的输入记录持久化，A-K 收到一次回复，B-K 与 G 均无该文本。
5. J 通过通信工具给 B 发 `DM03-j-to-b-0001`；B 得到通知，在 B-J 回复，J 收到正确来源。
6. J 给 K 发 `DM04-j-to-k-0001`；K 按脚本回复一次，J 在同一个 J-K 会话接收。
7. 将以上方向全部反转；验证 B→A、B→J、K→A、K→J。
8. 同时发送 A-K、B-K、J-K 三组带不同 nonce 的消息；检查每个 Session 输入与最终界面对应关系。
9. 让 K 在 G 内保持受控处理中，再向 A-K 发私信；检查群上下文未被 steer、注入或附加该私信。
10. 在不同会话中预埋不同 canary 文本；回复与接收上下文不得夹带其他私聊 canary。
11. 以一对尚无私聊的测试身份同时从两端创建会话，重复提交创建请求并关闭重开；验证数据库只有一个规范双方键，双方拿到同一会话 ID。

### 5.2 共享群与正确唤醒

1. A 建立 G，按稳定身份邀请 B/J/K；完成协议要求的成员接收后，B 从原侧栏进入 G。
2. 对比两端全局群 ID、成员身份和成员版本；群名相同不能代替群 ID 一致的断言。
3. A/J/B/K 依次发送一条普通文本；等待提交后对比两端消息集合、顺序、发送者与 nonce。
4. A @K，J @K，B @J，K @J；每次核对实际接收者，不只核对显示名称。
5. A @B、K @A；只检查人类通知与消息可读性，断言没有因此新增 Bot 模型调用。
6. J 发一条无 @ 的普通 Bot 回复；断言其他 Bot 未被自动全员唤醒；K 方向再测一次。
7. 分别检查 admin 和 mentionsOnly 模式；前者只默认调用指定管理员，后者普通发言不调用 Bot。只有 @Human 时两者都不额外调用管理员。
8. 把 J/K 均改名为 Chief，再进行步骤 4；旧消息 sender 与 replyTo 保持原身份。
9. 检查两端头像、成员列表、@菜单和消息头的本地/远程标记恰好相反，实例简称一致。
10. 回复 G 内一条指定消息；两端显示正确父消息。再构造私聊消息 ID 作为 replyTo，确认请求被拒绝。
11. 同时在 G 与 A-K 发送相同文本；仅靠 conversationId/messageId 区分，任何回包不能按最近窗口归类。
12. 刷新两端、关闭重开群，再检查历史、未读和回复跳转；不能只验收内存中的实时气泡。
13. K 离线期间发送一条 @K，重连后检查原 deliveryId 被消费一次；再次刷新和回放相同历史时不新增消费。
14. 管理员离线时，原投递保持等待且不自动改叫另一个 Chief；移除管理员时，Hub 原子切换为 mentionsOnly 或指定新的合法管理员。

### 5.3 文本边界

- 分别通过粘贴、拖拽、附件按钮及直接调用接口提交非文本内容；客户端禁用或提示，服务端拒绝。
- 文本中包含 URL 可以作为普通文字传输；不能自动把本地文件路径或私聊链接变成跨端可读附件。
- 发送表情、中文、换行和接近协议长度上限的文本；超限明确失败，不静默截断为另一条消息。
- 断言拒绝内容没有进入接收端历史、Bot inbox 或自动下载路径。

## 6. 故障注入与持久化证明

每个注入点需要可定位的测试钩子或代理规则，并记录“到达注入点”的证据。
注入必须作用于真实 Hub、真实宿主和测试数据库；仅单元测试模拟成功回调不算本节通过。

| ID | 注入位置 | 恢复后必须观察到的结果 |
|---|---|---|
| FI-01 | 客户端断网后发送，尚未发到 Hub | 持久本地队列保留文本与 ID；重启客户端后补送一次 |
| FI-02 | Hub 收到消息，数据库提交前崩溃 | 没有 durable ACK；原 ID 重试后只生成一个提交记录 |
| FI-03 | Hub 持久化提交后、ACK 发送前崩溃 | 重连重试返回原提交与原 conversationSeq，不新增第二条 |
| FI-04 | 代理丢掉 Hub 的 ACK，连接保持 | 超时重发幂等；发送端最终收敛到真实提交状态 |
| FI-05 | Hub 向接收端投递，接收 inbox 提交前崩溃 | 不发送“已持久接收”ACK；恢复后 Hub 补投 |
| FI-06 | 接收 inbox 已提交、ACK 丢失 | Hub 重投只命中原 inbox 记录，界面和 Bot 不重复消费 |
| FI-07 | 同一消息连续重复 3 次，再延迟重发 | 同一 messageId 只展示一次，每个接收者只有一个逻辑投递 |
| FI-08 | 按 seq 1、3、2 到达 | 保留缺口并补齐，稳定排序；不能把 3 的 ACK 当作 2 已存在 |
| FI-09 | 永久丢掉 seq 2，重连获取增量 | 补拉缺口成功；无法补齐时明确显示缺口，不能越过后宣称历史完整 |
| FI-10 | a、b、Hub 分别在有积压时重启 | 使用原身份、会话与游标恢复，不新建同名假群、不丢待发消息 |
| FI-11 | inbox 已入库、尚未提交给 DSH 时杀宿主 | 重启扫描待注入项，交到原 conversationId 绑定的 Session |
| FI-12 | DSH 已持久接收、插件尚未写回注入状态时杀进程 | 用稳定 deliveryId 查证已接收，完成状态修复，不盲目再注入 |
| FI-13 | DSH 调用返回前连接或宿主崩溃，结果未知 | 判定已入/未入后恢复；未知状态不能假称完成或直接丢弃 |
| FI-14 | 连续重连并重复订阅同一会话 | 保持一个逻辑订阅范围，消息与人类通知不按连接数翻倍 |
| FI-15 | ACK 后杀进程再读数据库与界面 | 已确认的 durable 记录仍存在；发送 Promise 成功不能替代此检查 |
| FI-16 | Bot 最终回复在 DSH 持久化后、outbox 提交前崩溃 | 通过原源事件补入 outbox，回到正确会话，不重新调用模型生成替代回复 |
| FI-17 | 输出映射/outbox/导出游标事务提交中或提交后崩溃 | 三者原子恢复；重扫只复用原 messageId，不漏发、不重复生成发言 |

### 6.1 DSH 与插件跨存储窗口

- 插件 inbox 和 DSH Session 不是同一个数据库事务，需要单独验证交接，不能用“SQLite 已提交”一笔带过。
- 验证公开 API 能否持久保存并查询 `deliveryId` 对应的输入来源；字段名以实际实现为准。
- 在“调用 DSH 前”“DSH 已持久化后”“插件回写前”三个边界分别注入崩溃，记录真实命中的边界。
- 重启恢复应查证原 Session 中是否已有该逻辑输入，再决定补交或修复插件状态。
- 如果当前公开 API 无法消除歧义，记录 `injection_unknown` 并报告能力缺口；该用例为 `BLOCKED`，不能改成通过。
- 只把消息永久留在 unknown、要求用户重发或静默跳过，均不能满足“不丢消息”的验收条件。
- 最终证明应包括原 ID 的持久记录、正确 Session 的输入记录、单次预期消费及一次可见回复。
- 恢复投影和重新拉取历史只能更新显示；不能因此再次调用所有群成员。
- 对 Bot 回复导出另保存稳定源事件、会话绑定、messageId、outbox 和导出位置的证据；测试换段后的旧段待导出回复仍可找回。
- 无法通过公开 API 找回持久输出时记为 export_unknown，对应项为 BLOCKED，不能只验收入箱就宣称完整收发可靠。

### 6.2 送达状态

至少区分本地待发、Hub 已持久提交、接收端已持久接收、Bot 输入已确认、明确失败和结果未知。
状态名称可以不同，语义与证据必须对应；“Hub 已接收”不能显示成“对方 Bot 已读取”。
进程退出前尚未确认的消息，重启后应显示原 ID 的恢复状态，不产生新的乐观成功消息。
发送拒绝或撤权属于有原因的失败，保留可审计记录；不能把失败伪装为网络仍在重试。

## 7. 认证、成员变化与历史范围

1. 分别使用未认证、过期、被撤销的实例凭证连接 Hub；发布目录、订阅、发送与 ACK 均应失败。
2. 实例 a 尝试冒用 instance b、用户 B 或 Bot K；服务端根据认证绑定校验来源，不能只相信 payload。
3. 非 G 成员尝试订阅 G、拉取历史、发送消息及读取 replyTo；每条路径都验证服务端权限。
4. 断开 b，在 Hub 累积发给 K 的群消息，随后撤销 K 的成员资格，再连接 b。
5. 对尚未授权交付给 K 的积压投递，按最新成员版本丢弃执行，终态明确为 `rejected/permission_revoked` 或协议等价状态。
6. 保留消息提交与拒绝投递的审计记录；K 的 inbox/Session 不得接收撤权后不再允许的积压正文。
7. 如果本地已有未消费 inbox，再撤权，则接收端消费前再次校验并标记拒绝，不能继续注入 DSH。
8. 已交付给对方的历史内容不能承诺远程抹除；撤权后断开增量、历史查询和新的投递权限。
9. 重新加入 K 应产生新的成员版本/加入序列；不得自动复活此前因撤权而拒绝的投递。
   保留同机 B 的群资格，验证 K 不能借共享缓存读取自己退出期间的消息；targetStored 但未 aiAccepted 的旧项仍被撤销。
10. 新建测试用户 C 后加入 G，默认从 joinSeq 起读取，分页和搜索也不能绕过该界限。
11. A 显式选择一段旧摘要分享给 G；摘要作为新消息发送，C 可读且能看见分享者与时间。
12. 自动摘要、回复预览、通知正文均不得夹带 C 未获授权的历史或任意私聊内容。
13. 保持 B 从序号 1 入群，K 从较晚的 joinSeq 加入；K 无法从同机缓存、搜索或直接 messageId 查询获得此前内容，也不会因等待无权读取的序号而卡住同步。
14. J 发一条新消息引用 K 入群前的旧消息：K 可见新正文和受限引用占位，不能读到旧原文；显式分享的新摘要可以正常读取。
15. 仅加入 K 而未加入 B 时，不因同机拥有 Bot 就自动给 B 开通共享群成员视图。

## 8. 本地兼容回归

- 不连接 Hub，创建本地 Bot 和本地群，验证原有私聊、@成员、普通回复与历史读取。
- 同时存在本地群和联邦群，使用相同显示名称，验证打开、发送、回复与未读都按身份隔离。
- Bot 的本地会话切换到新段后，联邦私聊仍绑定正确会话；旧 Session ID 不成为跨端身份。
- 停用联邦连接后，本地聊天仍可使用；远程联系人明确离线，待发状态不被显示成本地失败。
- 从旧格式数据启动并完成升级，再重启读取；保留旧 Bot、群、会话映射与本地历史。
- 仍只按测试目录执行迁移；不得用真实用户的 DSH_HOME 做回归样本。
