# 给本地 AI 的开发交接说明

## 目标

在 `KarlToon-FFAC/DS-Bot` 实现跨实例的人与 Bot 可靠通信。用户目前只有一台机器，先用两个独立 DSH Web 实例模拟双方，再补充不同 IP 的网络验证。

用户已经明确要求：**只做信息交流，不做任务管理。**人和 AI 能正确收发、身份明确、会话不串、正常断线与重启可恢复即可。任务、设计、审核、开发和进度可以由外部系统处理，不能因此新增内置流程。

用户另有明确说明：**开发中需要 API key 或其他必要东西，直接问用户即可。**这项许可不是让你从现有凭据文件中自行搜索密钥，也不是让你把密钥提交到仓库。

## 先读取这些文件

1. 仓库根 `AGENTS.md`。
2. `docs/plans/2026-11-03-federated-communication.md`。
3. 本目录 `protocol.md`、`development-environment.md`、`implementation-plan.md`、`acceptance.md`。
4. 根据改动继续读已有群聊、角色权限和 UI 标准。

基线是 DS Bot `0.2.6` / `5c514ad70d5f3fd1c3b72b2e76e530bef50989d7`，DSH 使用 `0.2.1-rc.4` 验证。新版本若改变公开 API，先记录差异，不静默升级全部依赖。

## 开始开发

先确认当前仓库、远端地址、工作树和用户已有修改。从方案分支取得全部文档：

```powershell
git fetch origin
git switch --track origin/docs/federated-communication
```

如果本地同名分支已经存在，使用 `git switch docs/federated-communication`；不要强制覆盖。如果有未提交修改，使用隔离 worktree 或保留修改，不执行 `reset --hard`。

在用户要求开始实施后，按实施计划使用一个实现分支，例如 `chore/federated-communication`，或沿用用户指定的分支。当前方案创建时 fork 只有 `main`，没有 `dev`；不要为满足上游模板擅自同步另一条上游开发线。

接下来按顺序：

1. 核实 Node、pnpm、端口、插件目录以及测试数据路径。
2. 跑基线构建和测试，记录已有问题。
3. 启动两个隔离的测试 DSH 与 Mock 模型。
4. 先完成 P0：身份隔离、正确会话、只显示不唤醒，以及公开 API 的入箱、Bot 输出导出与重启对账。
5. 通过后实现持久通信服务、收发队列、人/Bot 适配和 UI。
6. 按验收矩阵逐项验证，保留可复现的脱敏证据。

不要先做全套界面，再发现消息不能可靠进入 DSH。不要用一个进程里的假 Bot 代替最终双实例验收。

## 缺条件时怎样向用户询问

一次说清楚缺少的项目、用途和被阻塞的步骤，优先合并询问。可以继续已经具备条件的独立工作。

| 缺少的东西 | 应向用户说明 |
|---|---|
| 模型服务 | 需要服务地址、API 类型、模型 ID；API key 建议由用户在本地环境变量或 DSH 设置中配置 |
| Node/pnpm 或依赖安装受阻 | 实际版本、失败命令、脱敏错误、可选的用户已有环境；不要反复盲重试 |
| 仓库路径或测试目录 | 需要确认哪个 checkout、哪些目录可用于隔离测试；不得动用户真实 DSH 数据 |
| 端口或网络条件 | 哪个端口被占用、可选空闲端口；不同 IP 验证需要何种可达地址 |
| 运行公开 API 的关键缺口 | 最小复现、确认过的文档、具体无法满足的验收；禁止偷偷补丁修改 DSH |
| 需求范围不清 | 只问会影响通信行为的缺口；不要主动扩展为任务管理或审批系统 |

真实 API key 缺失不妨碍 Mock 通信测试。若确实需要真实模型验证，明确询问用户；不要编造 key、随意复用其他项目密钥或把 Mock 结果写成真实测试通过。仓库 Mock 使用的 `mock-key` 是本地测试协议占位，仅配对应的 loopback Mock 服务。

## 必须保持的通信边界

- A/B 是不同的人，J/K 是不同的 Bot；身份不按显示名或 IP 推断。
- 群和私聊各有稳定会话 ID；同一 Bot 在不同会话中的上下文不能自动混合。
- Bot 给人发私聊只通知人，不把 Bot 的话伪装成人类消息又喂给自己。
- 群事件同步给各端用于展示；未完成的投递按原收件资格继续消费，历史回放不重新创建投递。
- 相同消息重传使用原 ID，落盘、回执、入箱和已读分别表示。
- DSH 与插件存储之间的入箱和回复导出都必须对账。无法确认的结果保持未知并阻塞相应验收，不能盲重投、也不能假报成功。
- 旧本地私聊和记忆不自动上传；远程 Chief 不获得本机所有者权限。
- 首版文本/Markdown/同会话引用，附件明确不支持；正文不能静默截断。
- 不引入 `taskId` 驱动的业务任务、设计审批、开发执行器或跨会话业务控制。

## 实施授权与收尾

常规代码修改、隔离测试、修复和按用户指令提交可以持续推进。缺少必要资源就询问用户；发布公网服务、迁移真实用户数据等新范围，不能从本次通信开发授权中自行推导。

遵守仓库构建、lint、测试与 smoke 门禁。只更新源文件后生成 `client.js`。服务端包和插件发布包的依赖要在干净安装环境验证。

完成时交付：可运行代码、实际有效的启动/停止命令、双实例演示、逐项验收结果和未完成事项。区分“已实现”“已验证”“等待用户条件”。说明测试过的版本、平台和网络范围；不要将 loopback 验收写成真实跨机器部署已通过。
