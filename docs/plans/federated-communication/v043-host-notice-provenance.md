# V0.4.3：宿主通知不应污染通讯输入来源

## 复现

2026-11-18，以 V0.4.2 为基线。合成 SQLite 入站与 Session 事件中，同一回合
加入 SDK 生成的 `{kind:'model-selection',form:'notice',summary:'…'}`：
入站筛选、工具来源解析、收尾输出检查三个回归在原代码上全部失败。
原因不是多个通讯投递争抢一个输出，而是模型切换通知以 user/message 记录，
只识别 runtime-context snapshot 的筛选把它当成了待验证的 Hub 输入。
工具公共前置因此连带拒绝回复、报告与咨询；收尾检查另报 OUTPUT_SOURCE_UNKNOWN。

## 修复

四处共用明确的宿主元数据分类：模型请求入站、工作开始记账、工具来源、
最终输出归属。只忽略有效 runtime-context snapshot、既有工作目录/指令/工具
注册元数据，以及有合法 notice/summary 形态的 model-selection。
不把所有 `form:notice` 都当可信，也不根据正文中的“模型切换”字样判断。
元数据本身不能提供 delivery grant，只有元数据而没有真实入站仍然拒绝。
真实输入仍验证会话、收件人、成员纪元、delivery/message ID、AI 标志与撤销状态。

同绑定多个有效输入保留既有最近输入规则，不是要求输入条数必须为一。
真正混入用户输入、未知来源或其它绑定/纪元时，对外发送仍拒绝，不降级为无来源发送。
普通本地工具权限不新增限制。报告与新咨询保留真实来源关联，因为该关联还用于
去重、审计及把异步结果送回原任务；不能靠删除这段关联修复错误。
对已经保存且属于当前 Bot/绑定的咨询结果，轮询是读取，跳过不必要的发送来源解析。

## 失败可见性与 SDK 限制

使用公共 HarnessError 保存插件侧机读码；工具失败立即说明本次操作没有发送，
不要同回合反复重试或换无来源通道。工具来源/收尾来源失败写入通信活动与 diagnose，
含固定阶段、不含原始异常正文。后续系统提示说明上次阻断原因，不冒充本回合永久阻断；新入站来源校验成功会解除
该工具来源阻断标志。思考及普通收尾正文仍不自动外发。

真实 DSH 测试发现，0.2.1-rc.4 / 0.2.2-rc.1 的钩子异常终态只专门保留
LLM/工具激活错误，普通插件错误即便是 HarnessError 仍写 `turn/end.error.code=UNKNOWN`。
这是公共接口当前的限制。没有修改 DSH、改写既有日志、伪造 LlmError 或
ToolActivationError。具体插件错误码由活动、诊断及工具结果提供，异常文字也携带固定错误码前缀，
使原始日志仍可对账；原始内核
turn/end 的 UNKNOWN 尚需 DSH 上游支持通用 HarnessError 才能彻底消除。

## 原生验收

`DSH_HARNESS=… node ds-bot/dev/communication/model-notice-acceptance.mjs`
启动两个隔离 DSH、独立 Hub 与 Mock，先产生一次正常回复，再对同一 Bot 的同一
远程 Session 连续切换三个模型路由：验证 SDK 实际生成 model-selection notice，
群回复、本机未发布 Bot 咨询/结果读取、向本机 Chief 报告均成功。
最后注入真正未知来源：阻断继续生效，活动暴露具体输入错误码，同时记录 SDK
原始终态码，以明确区分产品可见诊断与内核限制。测试不读取生产用户数据或密钥。

新增恢复验收：真实未知输入失败后，再发一条有有效投递凭据的新入站，同一个
Session 成功回复并清除过期来源错误，不重置、不重放失败回合。

验证结果：插件 2,304 项，2,299 通过、5 项条件跳过、0 失败；Hub 226/226；
桌面 231 通过、1 条条件跳过。DSH 0.2.1-rc.4 相关来源回归 39/39，
两版 DSH 原生双实例模型切换/本机协作均通过；0.2.2-rc.1 还验证了来源失败后的
新入站恢复。宿主 Mock 冒烟 52/52；lint、生成产物和空白检查通过。
全部测试只使用独立临时实例、合成数据与 Mock。
