# F4 saved-publication state and F6 evidence follow-up

These fixes were tested as pending work on V0.2.8, then included in the user-approved
[V0.2.9 upgrade](release-0.2.9.md). The original evidence below retains its actual
pre-upgrade test version. No protocol or required capability change is needed.

## F4: confirmed save is different from an applied publication

The previous guard compared the loaded runtime with `rt.config.communication`.
A public Config Editor implementation can save the configuration without changing
that running plugin instance's options. In that window the comparison misses the
change, and Bot-scoped operations fall through to misleading publication or
membership errors. The original regression fixture updated memory immediately,
so it did not model the reported save-only behavior.

After a successful public editor transaction, the plugin now retains a scoped
receipt of the desired publication selection and lifetime generations. Reads
compare that receipt with loaded publication settings as well as live options.
The receipt never crosses Hub/device configuration boundaries. A hide/republish
cycle stays pending even if the original selection returns, because the lifetime
generation changed. A failed write does not create a successful-save receipt.
A newly loaded runtime using the saved settings clears the pending comparison.
No Host internals, configuration-file reader or DSH patch is used.

`publish-bots` still acknowledges the local save, with explicit fields:

```json
{
  "publishedBotIds": ["session-<native-Bot-id>"],
  "reloadRequired": true,
  "reloadReason": "publication",
  "publicationStatus": "saved-pending-reload"
}
```

Until the new settings load, Bot-scoped API/CLI operations and communication tools
return `PUBLICATION_RELOAD_REQUIRED`, with the same reason/status metadata.
`state` exposes `reloadReason`, and diagnostics distinguish the confirmed pending
save from a missing loaded publication. Other communication-setting changes keep
`COMMUNICATION_RELOAD_REQUIRED`. Recheck loaded state and current identities/epochs
after supported Host reload; saving alone proves no Hub publication or group join.
CLI `--help` and the packaged Agent instructions explain this boundary.

Post-reload archive verification uses an owned Bot DM and that Bot's exact epoch.
The change does not authorize group archiving through a private-record context or
substitute the Human's epoch for a Bot's membership.

## F6: corrected field evidence and authoritative diagnosis

The user's follow-up established that the failing target was absent from both
`contacts` **and** the group's `members`; its instance had been revoked/departed.
`UNKNOWN_MENTION` is correct for that target. The original reproduction does not
establish that a current group member outside the contact directory is rejected.
The parser parameter named `contacts` is not proof of directory-only validation:
`CommunicationRuntime.message()` supplies the current conversation's roster when
available.

The actual missing-contact topology is now exercised with two isolated native
DSH instances: A requests contact; B accepts with an explicit scope containing
only its first Bot. B later publishes another Bot that never appears in A's
contacts. B's Human becomes a group administrator and adds that unshared Bot.
A's real CLI send mentions the new current member; the Bot produces a real Mock
reply. The case also passes after a Host restart. A separate published outsider
remains outside the group and is correctly rejected. Retirement still returns
`BOT_RETIRED`, including for an identity that never joined the group.

The scoped `conversation.members` mention preflight now explicitly validates
current membership after checking retirement, independently of directory consent.
It does not publish a message, change membership or consume a message sequence.
The final message publisher keeps its own authoritative validation. Contact status
cannot grant membership in a conversation.

CLI previously reduced API errors to `{code}`. A code-only error therefore could
not identify its validation source. Known publication and mention errors now keep
safe, locally defined descriptions and allowlisted diagnostic fields:

- `mentionValidation.source: "hub"`: the authorized read-only Hub preflight rejected
  the target; `message.publish` was not sent.
- `mentionValidation.source: "refreshed-conversation"`: validation rejected the
  target/text after an authorized roster refresh. Metadata can include the roster
  version, request/member counts and unresolved exact principal IDs.

No raw exception text, credentials, message bodies, arbitrary upstream fields or
unbounded trace lists are copied into these error details. Existing safe retry IDs
and caller intent are preserved; failed sends are not automatically replayed.

## Verification

Reproducible native acceptance:
`ds-bot/dev/communication/field-f4-f6-acceptance.mjs`.
It uses the public Config Editor on two fresh owned DSH profiles, a real local Hub,
actual CLI subprocesses and deterministic Mock. No production devices, real LLM
keys or user DSH data are involved. The save-only pending window is additionally
covered by an editor fixture that deliberately leaves loaded options unchanged;
native automatic reload timing may complete before the next CLI subprocess runs.

regression and smoke totals and the seven native acceptance cases. Plugin: 2,059

DSH Mock smoke: all 52 steps passed. Lint and generated-client freshness passed. The original Windows deployment is not used as a test
endpoint. Deploying this source requires loading/restarting the relevant Host. The subsequent
user-approved version upgrade is tracked separately in the release note. No reset is needed.
